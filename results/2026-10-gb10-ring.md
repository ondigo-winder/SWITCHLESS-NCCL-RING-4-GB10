# Results: 4 × Dell Pro Max GB10 switchless ring, October 2026

## Setup

- 4 × Dell Pro Max GB10, DGX OS 7.6.0, kernel 7.0.0-1019-nvidia, driver 580.178.04
- ring: node1 –f0– node2 –f1– node3 –f0– node4 –f1– node1, one QSFP cable per edge,
  both PCIe halves addressed, MTU 9000
- bootstrap over a 10 GbE management LAN (`enP7s7`)
- container `nvcr.io/nvidia/pytorch:26.09-py3` used only as a CUDA 13 runtime;
  the benchmark is `tests/allreduce.cu` linked straight against the library under test
- bus bandwidth = bytes × 2(n−1)/n / time, float32 sum, 1 GPU per node

### What a switchless ring cannot do

Point-to-point traffic between ranks that share no cable has no path. This is a
property of the ring, not of this patch: v0.0.1 behaves the same.

| Operation | Result, v0.0.1 and this patch |
| --- | --- |
| send/recv to rank + 2 (opposite node) | fails at connection setup: `ibv_modify_qp ... Connection timed out`, then `unhandled system error` |
| all-to-all (grouped send/recv to every rank) | hangs during connection setup; stopped after 60 s |

In practice: tensor parallelism and pipeline parallelism between neighbouring
ranks work; expert parallelism (all-to-all) and any direct traffic between
opposite nodes do not.

## vLLM with a large model: Qwen2.5-72B-Instruct, BF16, tensor parallelism 4

Same image and launch as above, `--max-model-len 8192 --gpu-memory-utilization 0.75`,
33.9 GiB of weights per rank. Each library ran with its own settings (v0.0.1: 2 HCAs,
4 channels; this patch: 4 HCAs, 8 channels), fresh random prompts per run (new seed,
so no prefix-cache hits), `--ignore-eos`. One run per configuration.

| Workload | Metric | v0.0.1, 2 HCAs | this patch, 4 HCAs | Difference |
| --- | --- | --- | --- | --- |
| Prefill: 48 prompts × 4,096 tokens, 1 output token, concurrency 16 | tokens/s | 893 | 982 | +10% |
| | mean TTFT | 62.0 s | 56.0 s | −10% |
| | f0 cable, mean / peak (1 s) | 27.4 / 29 Gb/s | 30.2 / 32 Gb/s | |
| Decode: 64 prompts × 256 in / 256 out, concurrency 32 | output tokens/s | 132.0 | 134.7 | +2% |
| | mean TPOT | 220 ms | 217 ms | −1% |
| | f0 cable, mean | 8.8 Gb/s | 9.0 Gb/s | |

All requests succeeded, no NCCL warnings, RoCE and PHY error counters stayed at 0.

What this shows:

- The fabric is far from full with this model. Prefill needs about 30 Gb/s per cable
  (about 3.9 MB of all-reduce traffic per token per rank at about 1,000 tokens/s);
  decode about 9 Gb/s. GB10 compute and memory bandwidth are the limit, not the link.
- Even so, prefill came out about 10% faster with both halves. In tensor parallelism
  every all-reduce sits on the critical path, so a shorter transfer time helps even
  when the average load is low. With one run per configuration, treat the exact
  figure as indicative.
- Decode is latency-bound (160 small all-reduces per step); the difference is within noise.
- A model with a larger hidden size, FP8/FP4 weights (more tokens/s per node) or
  larger batches would push the fabric harder; that is where the extra bandwidth
  should matter most.
